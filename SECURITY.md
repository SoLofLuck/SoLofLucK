# Security

SoLofLuck has two Solana programs and both hold real money. This document
states the attack surface, what protects each part of it, and — explicitly —
**what does not**.

It serves two purposes: someone reading the code knows where to look, and we
never have to make an unverifiable claim like "everything is secure".

---

## Audit status — the honest version

**These programs have NOT been through an independent security audit.**

What has been done:

| Layer | Scope |
|---|---|
| Unit + scenario tests | luck-game 33, luck-distributor 20 tests |
| Chaos test (game) | 8 seeds x 400 random steps, 7 invariants checked at every step |
| Chaos test (distribution) | 4 seeds, 8 invariants at every step plus forged-claim attempts |
| Sabotage test | Every check was proven to ACTUALLY fail when removed |
| ABI check | 248 checks — that the client and the program speak the same bytes |
| Tokenomics check | 73 checks — that the published numbers agree with the on-chain rules |
| End-to-end rehearsal | On devnet: contribution -> list -> merkle -> distributor -> claim |
| `clippy` (strict) | On every PR, warnings count as errors |
| `cargo-audit` / `cargo-deny` | On every PR plus weekly — dependency advisories |
| The on-chain package set | Pinned; advisories are checked against that set |
| Chain/source match | A bytecode sha256 comparison on every deploy |

> The test counts are of the tests **we wrote**. On top of them `cargo test`
> also runs one test generated by Anchor's `declare_id!` macro, so the output
> shows one more per program.

What has not been done:

- An independent third-party audit
- A formal bug bounty programme
- Formal verification

The layers above look for **mechanical** errors. **Design** errors — "can this
rule be exploited economically?" — need a human to look. This document exists
to help that human.

## Dependencies — which question we are asking

`cargo audit` scans `Cargo.lock`. But `Cargo.lock` contains the **entire Solana
validator/TLS stack** pulled in for tests: `h2`, `quinn` (QUIC),
`rustls-webpki`, `ring`, `tokio`, `curve25519-dalek` and so on. On the first
audit run 10 "vulnerabilities" appeared and **none of them** was inside the
program uploaded to the chain.

Auditing `Cargo.lock` as if it were the on-chain program is a category error.
The right question is: **which packages enter the SBF build?**

That is answered by computation, not by guesswork. `cargo metadata` states, on
every dependency edge, the target condition under which the edge applies
(e.g. `cfg(not(target_os = "solana"))`). Those conditions are evaluated for the
SBF target and the graph is walked:

| | packages |
|---|---|
| The whole of `Cargo.lock` (luck-game) | 204 |
| **Entering the SBF build** | **96** |

The 108 packages in between run on the test machine, not on the chain.

There are two gates:

1. **The on-chain set is pinned.** If a new package enters, the check fails and
   somebody has to ask "what is this package, and is it clean?".
2. **Advisories are checked against that set.** If a package in the set has an
   advisory, CI stops. Advisories in the test stack alone stay visible but do
   not block — if they did, CI would be permanently red because of upstream
   warnings we cannot fix, and a red CI quickly becomes an ignored CI.

`cargo tree --target sbf-solana-solana` cannot be used: standard `rustc` does
not know that target (Solana ships its own `rustc` fork).

## What the chaos test guarantees

Random scenario sequences are generated and the invariants are checked **after
every transaction**. The seeds are fixed: a failing run can be reproduced
exactly.

**Game (7 invariants):** the vault never falls below the rent floor · the win
count never exceeds the play count · the total paid is consistent with the win
count · once the window has closed the player can **always** cancel · a pending
game whose window is open can **always** be settled · the spin accounting is
exact.

**Distribution (8 invariants):** the vault plus every recipient account = the
total minted · nobody can take more than they are owed · the claimed amount
never decreases · `ClaimStatus` and the real balance are exactly equal · the
distributor's counter equals the sum of the individual records · the claimed
amount never exceeds what has unlocked at that moment (the schedule is computed
**independently**, without calling the program's own function) · a claim with
the wrong amount or with **somebody else's proof** is rejected · once the
schedule ends everyone receives their full share and no dust is left in the
vault.

That every check really does work was proven **by sabotage**: the program is
deliberately broken and the corresponding invariant is seen to fail. One
sabotage (a version that ignored the rent share in the vault) was caught by no
check at all — a separate, targeted regression test was written for that gap.

## Structural guarantees

These can be verified by reading the code; they do not rest on tests.

### There is NO withdraw instruction

The complete instruction list of both programs is exactly this:

```
luck-game       : initialize · update_config · buy_spins ·
                  register_delegate · play · resolve · forfeit_stuck_play
luck-distributor: initialize · claim
```

**Neither has an instruction that empties the vault.** Not even the program
authority can withdraw locked tokens. Tokens in the distributor can only leave
with a valid merkle proof, and only up to the amount earned.

That is a deliberate and **irreversible** design decision: we could not
intervene even in an emergency. In exchange, nobody has to worry that "the team
pulled the funds".

### The prize always goes to the player's own wallet

`resolve()` is permissionless — anyone can call it. But the prize is paid to
`player_state.player`, not to the caller. Settling somebody else's round is
purely doing them a favour.

### A claim cannot be redirected to another wallet

```rust
#[account(
    init_if_needed,
    payer = claimant,
    associated_token::mint = mint,
    associated_token::authority = claimant,   // <-- the signer's own ATA
)]
pub destination: Account<'info, TokenAccount>,
```

Anchor's `associated_token::authority` constraint forces the destination
account to be the signer's own ATA.

### The merkle root and the schedule cannot be changed

`initialize()` runs once, and afterwards there is no path that changes the root
or the vesting schedule. Once the list is published, nobody can change anyone's
share.

## Randomness — commit / reveal

The slot machine's result is determined like this:

```
digest = sha256( slot_hash ‖ entropy_slot ‖ player ‖ plays_count )
dice   = u64_le(digest[0..8])  % 10000     -> did it win
tier   = u64_le(digest[8..16]) % 10000     -> small prize or jackpot
```

| field | size | format |
|---|---|---|
| `slot_hash` | 32 | the hash of the block used, raw bytes |
| `entropy_slot` | 8 | that block's slot number, little-endian |
| `player` | 32 | the player's wallet address, raw bytes |
| `plays_count` | 4 | `plays_count`, little-endian |

**It is `sha256`, not keccak.** The game uses `solana_program::hash::hash`
(SHA-256); the distributor uses keccak in its merkle tree. The two are
different, and confusing them makes verification fail.

**Verify it yourself** — anyone can reproduce this vector:

```python
import hashlib
pre = bytes(range(32)) + (488_699_073).to_bytes(8,'little') \
    + bytes([7])*32   + (5).to_bytes(4,'little')
d = hashlib.sha256(pre).digest()
assert d.hex() == '3d54d1715c5d05dcfc12bb5dd95b197b078f3135b04aab6ead91103c1233cc6d'
assert int.from_bytes(d[0:8],'little')  % 10000 == 7597   # dice
assert int.from_bytes(d[8:16],'little') % 10000 == 4556   # tier
```

The same vector runs both in the Rust test (`golden_dice_vector`) and in the
ABI check (`check-abi`). So the description here cannot drift from what the
program actually does — if it does, CI fails.

`commit_slot` is written at the moment of `play()`; the result is then produced
from the hash of slot `commit_slot + reveal_delay_slots`. Because that slot does
not exist yet, **nobody** — us included — can know its hash.

**Why this was necessary:** if the hash of the same moment were used, the player
could preview the result for free with their wallet's `simulateTransaction`
before signing, and send the transaction only when it won.

**A skipped slot:** the target slot may have been skipped (its leader produced
no block). In that case the program uses the **first existing block after it**
(`find_slot_hash_at_or_after`) and folds `entropy_slot` into the hash input as
well. An exact match used to be required, and a skipped slot silently burned the
player's spin.

**Modulo bias:** the dice is produced from **8 bytes**, not 2. Because 65,536 is
not a whole multiple of 10,000, a 2-byte dice shifted every published rate
against the player by ~6.8% (0.5% -> 0.534%). At 8 bytes that bias drops to the
order of 5x10⁻¹⁶.

### A known limit: leader influence

The party producing a slot's hash is that slot's **leader**. In theory a leader
could influence the hash somewhat by choosing which transactions to include in
its own slot. This is the shared limit of all blockhash-based on-chain
randomness.

In our case the exploit makes no economic sense: the target slot is known at
commit time, the prize is capped at 1 SOL, and the cost to a leader of
engineering its slot's contents in its own favour is far above that. We still
do not claim "true randomness" — a VRF (Switchboard, say) would give a stronger
guarantee, at the price of an external dependency and additional cost.

## Points of centralisation — these do require trusting us

To be honest, there are three.

### 1. `update_config` — the game parameters

The authority can change the prize amounts, the win rates, the house share and
the package prices. That is needed to adjust the tariff, but it is also the
power to make the odds worse.

**It does not affect pending bets.** Every parameter that determines the payout
is copied into `PlayerState` at the moment of `play()`, and `resolve()` reads
those rather than the config. So your round settles at the odds that applied
when you placed your bet; it is not possible for the authority to see a pending
bet and change its odds.

> That was **not** the case before. `resolve()` read the current config, and
> the comment in the code said "it does not affect pending games" and then
> contradicted itself one line later with "resolve reads from the CURRENT
> config". In a game that claims verifiable fairness, "trust us not to change
> the odds after you place your bet" was an unacceptable gap. Someone reviewing
> the code from outside pointed it out; it was closed before launch, at the last
> moment when the fix was still free.

The vault's **balance** is not frozen, and must not be: "easy mode" depends on
how full the vault is at that moment, and that is deliberate — as the vault
fills, the odds improve for everyone. What is frozen is the **threshold**, not
the balance.

Its limits: every rate <= 100%, easy mode must be easier than hard mode, the
threshold must cover the jackpot plus its share, and the treasury cannot be the
zero address. **What it cannot change:** where the money in the vault goes. The
prize always goes to the player and the share always to the treasury.

Changes are public on chain — anyone can read the `GameConfig` account.

### 2. The presale buyer list

The list is read from the chain (`scripts/presale-buyers.mjs`) but **we are the
ones compiling it**. Once the merkle root is written to the chain it does not
change either.

The countermeasure: anyone can run the same script and produce the same list
themselves — they do not have to trust us. The script also verifies that the
history it scanned **accounts for** the wallet's balance today; if the RPC
history has been pruned it stops (otherwise the earliest contributors would
silently drop off the list).

### 3. The upgrade authority

The programs are upgradeable. We hold the upgrade authority.

That is needed to be able to fix bugs — but it also means being able to change
the program's behaviour. Closing upgrades permanently (setting the authority to
`None`) removes that risk and removes the ability to fix bugs with it. That
decision will be taken after TGE, once the code has been in real use for a
while.

On every deploy the on-chain bytecode's sha256 is compared against the build's
and written to the log, so the question "did the on-chain program come from this
source?" can be answered.

## If you find something

If you find an open security hole, **do not announce it publicly first**.
Report it through the contact channel in `SECURITY.md`; once it is fixed we can
announce it together.

> The contact address will be added here before TGE.

The bug bounty programme will be announced before launch. This section will be
updated once the amount and scope are published.

**A warning:** messages on Telegram or X offering to "audit your project for
free" are almost without exception phishing attempts. Nobody will be given
write access to the repository, a private key, or access to the deploy wallet.

```bash
# The chaos test with detailed output
cd program/luck-game && cargo test chaos -- --nocapture

# The ABI, tokenomics, tx-path and error-code checks
npm run verify

# That the on-chain program matches the source (in the deploy logs)

```
